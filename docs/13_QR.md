# PantryHub QR System

## Overview

This document defines the QR code system architecture for PantryHub.

QR codes are intended to provide fast interactions between users and devices.

The QR system should support:

- Household invitations.
- Temporary sharing.
- Data exchange.
- Device pairing.
- Future synchronization workflows.

---

# QR Philosophy

QR codes should simplify actions.

The user should not need to:

- Copy long identifiers.
- Type invitation codes.
- Configure complex connections.

The QR should represent:

```
Fast connection

+

Controlled access

+

Simple experience
```

---

# QR Types

PantryHub defines different QR purposes.

```
Household Invitation QR

Shopping List Share QR

Data Import QR

Device Pairing QR
```

---

# Household Invitation QR

## Purpose

Allows a user to join an existing household.

Example:

```
Create household

↓

Generate QR

↓

Family member scans

↓

Joins household
```

---

# Household Invitation Flow

```
Owner

↓

Creates invitation

↓

Generates QR

↓

Other user scans

↓

Authentication

↓

Accept invitation

↓

Household joined
```

---

# Invitation Data

The QR should not contain sensitive information directly.

Bad:

```json
{
 "email":"user@example.com",
 "household":"Family"
}
```

---

Recommended:

```json
{
 "type":"HOUSEHOLD_INVITATION",
 "token":"random_secure_token",
 "expiresAt":"2026-01-01"
}
```

---

# Invitation Token

The token should be:

- Random.
- Unique.
- Expirable.
- Single purpose.

Recommended:

```
UUID

+

server validation
```

---

# Invitation Expiration

Invitations should expire.

Example:

```
24 hours
```

or:

```
7 days
```

depending on user settings.

---

# Invitation Security

A QR invitation should not automatically grant access.

Flow:

```
Scan QR

↓

Validate invitation

↓

Show household information

↓

User accepts

↓

Join
```

---

# Shopping List Share QR

## Purpose

Allows temporary sharing of a shopping list.

Example:

```
Prepare party list

↓

Generate QR

↓

Friends scan

↓

Import list
```

---

# Share Modes

Possible modes:

## Copy

Creates a new independent list.

Example:

```
Christmas Dinner

becomes

Christmas Dinner Copy
```

---

## Collaborate

Future synchronization.

Example:

```
Everyone edits same list
```

---

# List QR Payload

Example:

```json
{
"type":"LIST_SHARE",
"listId":"uuid",
"permission":"COPY"
}
```

---

# Data Import QR

## Purpose

Allows quick import without manually selecting files.

Example:

```
Generate QR

↓

Scan

↓

Import data
```

---

# Limitations

Large datasets should not be embedded directly.

Avoid:

```
QR contains entire database
```

---

Preferred:

```
QR contains reference

↓

Retrieve or import data
```

---

# Device Pairing QR

## Purpose

Future connection between devices.

Example:

```
Phone A

↓

Generate QR

↓

Phone B scans

↓

Devices linked
```

---

# QR Data Format

All QR payloads should follow a common structure.

Example:

```json
{
"version":1,
"type":"HOUSEHOLD_INVITATION",
"payload":{
}
}
```

---

# QR Versioning

Every QR should include:

```
version
```

Reason:

Future compatibility.

Example:

Version 1:

```
LIST_SHARE
```

Version 2:

```
LIST_SHARE_WITH_PERMISSIONS
```

---

# QR Validation

Every QR scan must validate:

- Format.
- Version.
- Expiration.
- Permissions.
- Signature if applicable.

---

# Invalid QR Behavior

The user should receive understandable messages.

Bad:

```
Invalid token exception
```

Good:

```
This QR code is no longer valid.
```

---

# Permissions Model

QR actions should define permissions.

Possible permissions:

```
VIEW

COPY

EDIT

ADMIN
```

# QR Scanning Experience

The scanning flow should be:

```
Open scanner

↓

Detect QR

↓

Explain action

↓

Confirm

↓

Execute
```

---

# User Safety

Never execute actions immediately after scanning.

Example:

Bad:

```
Scan

↓

Automatically join household
```

Good:

```
Scan

↓

You were invited to:

Family Home

Join?
```
